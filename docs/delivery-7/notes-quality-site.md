## 1. What changed, per item

### R-120 — the site Go needs at least one Cursus verdict (NEW-SITE-1 "a")

- `goChantier` (`src/domain/site.ts`): with no verdict received the condition "Individual go · Cursus" stays open, sub-line
  "No Cursus verdict received" (`NO_CURSUS_VERDICT`), one open record, so the Go is "NO GO". A GO with reserve is still
  accepted; a NO GO still blocks. Test in `src/domain/site.test.ts` citing NEW-SITE-1.

### R-112 — ITP inspection results, NCR reported in Vigie on a failure (Q-6a, Q-6b, V-3)

- "Record result" on each plan line (`src/features/itpcom/result-button.tsx`, Server Function `recordInspectionResultAction`,
  writer `recordItpResult` in `src/server/dal/itp.ts`): Passed / Passed with reservations / Failed, the inspection date
  (required, not after the business date 30 Sep 2026), the inspector (required; a person is matched by name, a third-party
  inspector stays typed), the client representative present (required on a hold point, offered on a witness point, absent
  otherwise — Q-6a) and a comment (required for a failure — the non-conformity — and for reservations).
- Who: quality, the engineering lead and the director (`ITP_RESULT_ROLES`), on a project they may edit. The PM, the client and
  the others read. A new result replaces the previous one (re-inspection after a failure); the audit trail keeps each one
  ("result: Failed → Passed · date · inspector · comment"); the activity feed records it.
- Stale guard: the form sends the result the viewer saw; a line recorded meanwhile is refused ("This inspection has changed
  since you opened it") and the page refreshed.
- On the line: "Failed 29 Sep · Gabriel Comte · client N. Bensaïd" under the name, the comment, and — for a failed line
  without a Vigie NCR — "Report the NCR in Vigie": `vigieReportNcrUrl` (the single place where Vigie's `/signaler` parameters
  are built) with `projet`, `titre` = "ITP I-03 · Structure · Paint thickness (DFT)", and the new proposal `inspection=I-03`.
  When Vigie reports an NCR with that inspection (`VigieNcrRecord.inspectionNumber`, optional, mirrored in
  `vigie_ncrs.inspection_number`), the line shows the NCR number (opens it in Vigie) instead of the link (Q-6b). If V-3
  renames the parameters, only `links.ts` changes.
- P-10b: the client sees the result line but no comment, no Vigie link and no NCR number.
- A pass with reservations counts as passed (KPI "Inspections passed", system group "n / m", "Hold points ahead").

### R-114 — a deliverable rejected by the client goes back to In progress at the next revision (Q-3a)

- `rejected → in_progress` is a producer step, "Start next revision" (row and drawer; project team, never the client),
  `src/domain/quality.ts` `PRODUCER`, DAL `moveDeliverable`. The revision steps by `nextRevision` (A → B … Z → AA, case kept;
  0 → 1, 09 → 10; "P01" → "P02"; none → A; other → ".1").
- History: every client decision (accepted / rejected, revision, submission, date, who, comments) is a `deliverable_reviews`
  row (`decideDeliverable`). Starting the next revision clears the row's rejection, submission and acceptance window; a
  rejection recorded before the history existed (an older database) is first copied into the history. The drawer shows
  "Client review history" (newest first, comments as typed). The issued Codex document link is kept (the new revision is
  deposited in Codex and keeps the same link, as the item says).
- Stale guard: a second click on a stale "Start next revision" is refused ("This step is not available any more").

### R-115 — "New deliverable" for the project manager (Q-3b, A-14)

- On the deliverables register the header primary is "New deliverable" for the project's manager and the director (else
  "New NCR" as before). Form (`src/features/quality/deliverable-form.ts`): type (Settings › Deliverable types, active),
  title, due date, WBS element of the project (required: `wbs_code` is NOT NULL), responsible (R) and backup (B, optional,
  different from R) from the project team. Server Function `createDeliverableAction`, writer `createDeliverable` (role,
  ownership through `managesProject`, active type, WBS node, persons, numbering D-nnn after the project's highest).
  A, C and I stay empty until the RACI matrix of S-13b arrives.

### R-137 — client issues handled by the project manager (L-6, X-6, P-10b)

- Internal space: a "Client issues" card on the project's **Stakeholders & RACI** screen (`src/features/client-issues/`),
  shown to internal viewers, editable by the project's manager and the director. Steps: "Take in charge" (Open → In
  progress), "Answer" (the answer the client sees; an Open issue is taken in charge at the same time), "Close" (needs a real
  answer — given before or in the closing form; the automatic acknowledgement is not one). Closed issues offer nothing.
  Stale rows are refused. Writer `handleClientIssue` (`src/server/dal/client.ts`): role + ownership, optimistic status guard,
  audit + activity.
- Notifications (Keystone only; X-6b's e-mail channel sends nothing yet): the project's PM is told when the client raises an
  issue (link `/projects/<code>/stakeholders?issue=CI-08`, the row is highlighted); the client who raised it is told of the
  answer and of the closure (link to the portal's Issues tab). A notification failure never undoes the write.
- Client portal: the answer replaces the acknowledgement; the meta reads "Raised 22 Sep · Answered 30 Sep". The internal
  handling (who took it in charge, when) is never shown to the client (P-10b); the card is not rendered for the client.

### R-143 — warranty claims followed end to end (Q-8 "a")

- Claim drawer on Warranty claims (`?claim=WC-014`, rows clickable): steps Open → Diagnosed → Intervention planned → Closed,
  facts, design ECO (Keystone's ECO screen when Vigie reports it, else Vigie; or "Raise ECO in Vigie" = `vigieNewEcoUrl`
  prefilled with the machine's project and "WC-014 · issue"), the machine's as-maintained configuration, the claim's
  interventions with "Mark done", and the steps: "Edit claim" (coverage — warranty / extended warranty / chargeable —, owner,
  cost in k€ with 2 decimals, next step, diagnosis, ECO number), "Mark diagnosed" (with the diagnosis), "Plan intervention",
  "Close claim".
- Rules (`src/domain/claims.ts`): an Open claim is diagnosed first; planning an intervention moves a Diagnosed claim to
  Intervention planned (an Open claim stays Open: a diagnosis visit); closing needs a diagnosis and no intervention still
  planned, and is dated on the business date; a closed claim is read-only; a diagnosed claim keeps a diagnosis.
- Interventions: "Plan intervention" from a claim, or from the Interventions view's header (a preventive visit on a chosen
  machine); "Mark done" (date not in the future, report, optional part replaced / upgraded + revision fitted).
- Who: the Warranty claims workspace (director, PM, quality, procurement), as "New claim" — there is no after-sales persona.

### R-144 — machines and their as-built configuration created at delivery (E-8 "a")

- Installed base: a "Delivered projects" card lists the projects at stage Expédition or later (`isDeliveredStage`), of a
  machine type (not R&D), whose BOM carries parts with a revision, with the parts recorded as built and the machines already
  registered. "Register machines" (fleet editors; a PM only for their own projects) creates N machines (default: Σ assembly
  root quantities, at least 1; "name #1", "#2" when several), machine type, client and site of the project, delivered on
  (default: the business date) = warranty start, warranty end (default: delivery + the contract's warranty months − 1 day,
  "24 months from SAT" → 24; 24 when the contract says nothing), each with the as-built configuration: every BOM part with a
  revision, at its catalogue revision, once.
- Kept up to date by after-sales: "Mark done" with a part fitted upserts the machine's `machine_part_revisions` (a part of the
  configuration or of the catalogue), audited on the machine ("configuration: FD-DET-OPT2 A → B · IV-085").

### R-126 — photos stored in Keystone (X-15 "split", SC-4a "a")

- File store purpose `photo` (images only, 20 MB, content sniffing — `src/server/storage/files.ts`), 20 photos per record.
  Upload: `POST /api/photos` (Route Handler: files above the 1 MB Server Function limit; same-origin guard, capped body);
  image: `GET /api/photos/<id>` inline (thumbnails, full image in a new tab) or `?download=1`; remove: `removePhotoAction`
  after a confirmation dialog. Audit on the record ("photo added: …").
- Where: the goods-receipt drawer (gallery instead of the empty frame; a receipt photo is also a `receipt_attachments` row,
  so "Photos · n attached" counts it; the seed's counted photos without a file read "3 photos recorded without a stored
  file"), the Site daily reports and the Site punch list (a "Photos" column), the ITP punch list (camera button per row).
- Rights (`src/features/photos/access.ts`): add / remove = edit right on the governing screen (Deliveries, Site, Inspections &
  punch list) on that project, never the client; see = internal viewers; the client only the ITP punch list's photos of
  their own project (P-10b hides purchasing and the site's internal records).
