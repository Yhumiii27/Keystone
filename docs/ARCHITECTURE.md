# Keystone PM — architecture & conventions

Rebuild of the Claude Design prototype `design/Keystone PM v8.dc.html` as a Next.js full-stack app.
The functional spec lives in `docs/spec/` (00 overview → 11 data model). **Read the spec section of your screen
before coding, and the prototype template lines it cites** (`design/_extracted/template-annotated.html` has the same line
numbers with every `{{ T.kN }}` replaced by «English text»). Visual target: pixel parity with the prototype.

## Stack

- Next.js **16.4** App Router, React 19.3, TypeScript strict. This Next version has breaking changes vs. older
  knowledge: read `node_modules/next/dist/docs/` when unsure (async `params`/`searchParams`/`cookies()`,
  `proxy.ts` instead of middleware, `PageProps<'/route'>` / `LayoutProps` global helpers).
- Data: Drizzle ORM + PGlite (embedded Postgres, `./.data/pg`), migrations in `./drizzle` (generated by
  `npm run db:generate`), applied and seeded automatically on first DB access (`src/server/db/client.ts`).
  `npm run db:reset` deletes the local DB (stop the dev server first).
- Icons: `@phosphor-icons/react` — import from `@phosphor-icons/react/dist/ssr` (works in server and client
  components). Prototype `ph ph-foo-bar` → `FooBar`; `ph-fill` → `weight="fill"`. Size = prototype font-size.
- Tests: Vitest (`npm test`), files `src/**/*.test.ts`. Domain logic must have golden-value tests (docs/spec/00 §8.8).
- Scripts: `npm run dev | build | lint | typecheck | test | db:generate | db:reset`.

## Rules

### Routing & state
- Routes come from `src/config/screens.ts` (`screenHref(id, {code})`). Project-scoped screens live under
  `/projects/[code]/<slug>`. Never hard-code another screen's URL — use `screenHref`.
- View state that the prototype keeps in `this.state` (tabs, filters, selected row, open drawer) goes into **search
  params** (`?tab=`, `?view=`, `?act=`, `?q=` …, see docs/spec/00 §8.3) so it is linkable. Purely transient UI
  (popover open, form drafts) stays in client state.
- Server Components by default; `'use client'` only for interactive islands. Pass translated strings or data down.

### Data
- Business data is in the database, seeded from the prototype (`src/server/prototype/*.json` = all prototype
  constants, plus `initialProjects()`, `projectData(code)` for the 6 projects with data, `genPOs`).
- Read through `src/server/dal/*` (async functions, `import 'server-only'`). Write through Server Functions
  (`'use server'`) that validate input, check the viewer's permission, write, then `revalidatePath`.
- Store **codes**, never translated labels (the prototype's FR mode stored translated enum values — a known defect).
- Amounts: k€ unless the column name says `_eur`. Dates: ISO strings / `date` columns; display via `lib/format`.
- Time model: the data set is frozen at **status date Fri 25 Sep 2026** (`STATUS_DATE`, `TODAY=4`, `tNow=8.8`
  months). Use those constants, not the real clock, for anything the prototype computes against "now".
- Do not reproduce defects listed in docs/spec/00 §7.16 (e.g. `projectData()` falling back to Harbor Line data:
  show an empty state instead).

### i18n
- Write UI strings in **English, exactly as the prototype** (`tpl_keys.json` / the spec), and render them through
  `t()`: `const { t, lang } = await getI18n()` (server) or `useI18n()` (client). FR comes from the prototype
  dictionary + rules, so matching the English text verbatim gets the right French for free.
- Dynamic strings: build the English sentence the prototype builds (e.g. `` `${n} active projects` ``) and pass
  it through `t()` — FR_RULES handle the parameterised forms.
- Missing FR translation → add `"English": "Français"` to **your feature's** `src/i18n/extra/<feature>.json`.
- Money/dates: `money(k, lang)`, `moneyEur(v, lang)`; English date strings (`dateOf`, `fmtD`) go through `t()`
  (months are translated by the engine). Default language: French.

### Styling (pixel parity)
- Use Nocturne tokens only (`var(--color-*)`, `--radius-*`, `--shadow-*`, `--space-*`) and DS classes (`.btn`,
  `.btn-primary`, `.btn-secondary`, `.btn-ghost`, `.btn-icon`, `.tag`, `.tag-accent|-neutral|-outline`, `.card`,
  `.input`, `.field`, `.seg`, `.table`, `.dialog*`, `.elev-sm|md|lg`). No hard-coded hex colours.
- Copy the prototype's inline values (font sizes 10–26px, paddings, gaps, grid templates) exactly. Static styles
  in CSS Modules (`*.module.css`, colocated); `style={{…}}` only for data-driven values (widths, positions, colours
  picked from data). `style-hover` in the prototype → `:hover` in the module.
- Status tones are mono-accent (docs/spec/00 §7.14, 02 DS-TONES): `tag-accent` alert, `tag-outline` watch,
  `tag-neutral` calm; attention text `var(--color-accent-300)`.
- Reuse components from `src/components/ds` and `src/components/app` before writing new ones. Charts are SVG
  with the prototype's geometry (e.g. EVM 760×290).

### Permissions
- Viewer = `getViewer()`. `KEYSTONE_AUTH=demo` (default, tests): the persona of the "View as" cookie. `KEYSTONE_AUTH=entra`:
  the user signed in with Microsoft Entra ID (`src/proxy.ts` redirects without a session; `getViewer()` re-reads the user
  and redirects to `/sign-in` when the session is no longer valid). The Viewer carries `role` (active role), `roles`,
  `personId`/`userId` (null for demo personas), `email`, `department` and `organisation` (client users) — see
  `docs/delivery-7/notes-auth.md`. Per-user records are keyed by the user (`userIdOf(viewer)` in `dal/users.ts`), never by
  the role; client scoping uses `viewer.organisation`.
- Screen gating: `canSee(role, id)`. An internal role opening a screen outside its list gets it with the
  "Outside my workspace · Read-only" banner and no primary action (shell handles banner; screens must hide
  their edit controls when `outside` or `readOnly` — see the project context helpers). A client is sent to their
  Home instead (P-1), and refused every project of another organisation (P-10a).
- Rights (delivery 7 lot "rights", `docs/delivery-7/notes-rights.md`): the pure rules live in `src/domain/rights.ts`.
  Write rights on a project follow its named team (`project_members.project_role`: pm / deputy / referent / team, plus
  `projects.pm_person_id`); everybody else reads it (`readOnly`), the director edits all. The PM rights (stage,
  deliverables, plan structure, minutes, PO approval) follow `isLead` (PMs, deputies, director).

### Parallel work
- Each feature owns its folders: `src/app/(app)/<its routes>`, `src/features/<feature>/`, `src/domain/<its modules>`,
  `src/server/dal/<feature>.ts`, `src/i18n/extra/<feature>.json`. Do not edit other features' files.
  Shared files (`components/ds`, `components/app`, `config/*`, `lib/*`, `server/db/*`) belong to their owners;
  if you need a change there, add a new file next to them or note it in your report.
- Never run `npm install`, `db:generate`, `db:reset` or long-lived dev servers unless your task says so.
